# LOOP_CONTRACT ／ 自律ループ実行契約書

このファイルは **`/loop` コマンドから読み込まれ、Claude が自律的にタスクを進めるための実行契約書**。
各反復ごとにこの契約書を読み直し、記載順に従って行動する。

- 版数: 3.0
- 作成日: 2026-07-23 ／ 改訂日: 2026-07-31
- 対象プロジェクト: 予定管理システム(ScheduleManagement)
- ループ実行モード: **動的モード(自律ペーシング)**

> **2026-07-31 改訂の要点**：マスタ用日報メール本文見直し(§1.1)の残3項目を完了させた後、
> **新部門展開の準備**(改善タスク台帳 §12、#38〜#48)を次期ミッションとする。
> 現在「商品開発室」1部門のみの運用を、他部門にも展開できる状態に整備する。
> 進捗は [進捗ダッシュボード.html](進捗ダッシュボード.html) で常時可視化する。

## 0. ループ起動の呼び出し方(人間向け)

対話セッションで次を入力する:

```
/loop docs/進捗管理/LOOP_CONTRACT.md を読み、記載の手順で1タスク実装してください
```

初回起動後は Claude が自律的に **ScheduleWakeup** を用いてペースを刻む。停止したいときは以下:

- 一時停止: 「一時停止」「pause」「停止して」
- 完全終了: 「ループ終了」「stop loop」

| ② | 新部門展開の準備 | 改善タスク台帳 §12(#38〜#48) | 未着手 |

- 完了判定: ①は §1.1 の項目5〜7すべて完了。②は改善タスク台帳 §12 の「必須」項目(#38〜#41)すべて完了
- 副次目標: [進捗ダッシュボード.html](進捗ダッシュボード.html) と改善タスク台帳が常に最新の状況を反映していること
- #15(「切り替え」時の上長コメント一瞬表示)は監視継続中。新たな再現報告があれば都度対応(§2.2 参照)

### 1.1 マスタ用日報メール本文の見直し(2026-07-27 追加、①の対象)

現行の自動生成本文（`_build_master_body` in `mail_report.py`）の各セクションについて、
表示ルールと繁栄（＝情報の充実度・見やすさ）をユーザーと1セクションずつ確認しながら見直す。
対象セクション: 予定/実績サマリー・対応中タスク一覧・メンバー実績・振り返り・開発状況・次回予定。
1 反復では **1 セクション** のみ扱う（スコープを絞り、確認と実装を素早く回すため）。

#### 1.1.1 【2026-07-28 重大発見】「対応中タスク一覧」の紐付けが構造的に0件だった

4回にわたる「対応中」修正（実績ベース→週間予定ベース→タスク名完全一致補完）が
すべて「まだ駄目です」と判定された。エージェント分析の結果、**根本原因はロジックの
判定基準ではなく、データの紐付け自体が存在しないこと**と判明：

- `weekly_schedule.project_task_id` ／ `daily_result.project_task_id` は**全件 NULL**
- 週間予定のタスク名（`task_master` 由来の自由入力語彙）と `project_task.task_name`
  （ガントチャートの計画語彙）は**完全一致が0件**（例：`'M365検討'` vs
  `'M365パイロット結果反映・プログラム修正'` は人には同じ仕事でも文字列としては別物）
- そのため「判定基準をどう変えても出力は常に0件」という状態が4回続いていた

**ユーザー確定方針（2026-07-28）**：タスク名の一致に依存する設計を廃止し、
**大区分・中区分（category_id/subcategory_id）で結合する方式**に切り替える。
`task_master` にも `project_task` にも共通する区分列を使い、タスク名が一致しなくても
「対応中」を中区分単位のまとまり（理想形の「AI開発[配筋]」等）として集計する。

ユーザー提示の理想出力例（全文）は `LOOP_LOG.md` の本反復エントリに保存済み。
実装時は必ず参照すること。主な仕様変更点（**1〜4は完了済み**、5〜7が残作業）：
1. ✅「対応中」のグルーピング単位を「区分（大区分／中区分）」に統一
2. ✅ 子タスク行に担当者・進捗・状態を付与（開発状況セクションと同じ書式）
3. ✅「完了」除外条件を「終了日 < 対象日」に緩和（当日完了は表示する）
4. ✅ 開発状況セクションの担当者表示を姓のみに統一（`user_name_by_id` の生成ロジック修正）
5. 🔲 開発状況の中区分の並び順を明示的に制御（現状は全区分 display_order=0 でアルファベット順）
6. 🔲 次回予定の `📅` 絵文字を削除、イベント収集をマスタ自身のみに限定
7. 🔲「□予定」の括弧書き（入力率表示）を削除、指標の意味をユーザーと再確認

1反復では上記のうち実装可能な単位で1つずつ進め、都度ユーザー確認を挟む。

### 1.2 新部門展開の準備(2026-07-31 追加、②の対象)

**背景**：現在「商品開発室」1部門のみで運用中のシステムを、他部門にも展開できる状態に
整備する。事前調査（改善タスク台帳 §12.1）の結果、ユーザー・権限まわり（`dept_master`・
`user_affiliation`・4段階ロール・所属切替）は既にかなり多部門対応済みだったが、
**タスク区分マスタ（`task_category`/`task_subcategory`）が全社共通で部門分離できない**こと、
**Excel/PDF出力の見出しに「商品開発室業務進捗」がハードコードされている**こと、
**メール設定（`mail_settings`）が部門別化されていない**ことが主な不足点として判明した。

対象タスクは改善タスク台帳 §12.2（#38〜#48、優先度：必須／推奨／任意）。

**進め方**：
1. まず①(§1.1残3項目)を完了させてから着手する
2. 「必須」項目(#38〜#41)を優先度順に1反復1タスクで進める
3. #38（タスク区分マスタの部門分離）は影響範囲が大きいため、着手前に設計方針（`dept_id`列の
   NULL 扱い・既存データの移行方法）をユーザーに確認してから実装する
4. 「必須」完了後、「推奨」項目(#42〜#45)に進む。「任意」項目(#46〜#48)はユーザー判断があれば対応

## 2. 実行順序(1 反復 = 1 タスク完遂)

各反復で **1 つ** のタスクを完遂する。並列で複数のタスクに手を出さない。

### 2.1 起動チェックリスト(反復の最初に必ず実行)

1. [改善タスク台帳.md](改善タスク台帳.md) §1.1・§12 を読み、直近の完了状態を取得
2. [進捗ダッシュボード.html](進捗ダッシュボード.html) を Read し、直近の反復記録を確認
3. `git status` で現在のブランチ・uncommitted 変更を確認
4. [LOOP_LOG.md](LOOP_LOG.md) を開き、前回反復の記録があれば確認
5. 本番サーバーが稼働中か確認(`netstat -ano | grep :5000`)。DEV サーバーも同様に確認

### 2.2 タスク選択の優先順位

上から順に、最初に該当したタスクを実施する:

1. **§1.1 マスタ用日報メール本文の見直し・残3項目**(項目5〜7、①完了までの最優先)
   - 対象: 開発状況の中区分並び順制御／次回予定の絵文字削除・イベント収集限定／
     「□予定」の括弧書き削除
   - 1 反復 = 1 項目。着手前に対象項目と見直し方針をユーザーに確認する
2. **①がすべて完了したら §12 新部門展開の準備**(②、改善タスク台帳 §12.2)
   - 「必須」(#38〜#41) → 「推奨」(#42〜#45) → 「任意」(#46〜#48) の順
   - #38(タスク区分マスタの部門分離)は着手前に設計方針をユーザーに確認する(§1.2 参照)
   - 1 反復 = 1 タスク番号
3. **#15 の経過観察**：新たな再現報告があれば都度調査・記録。無ければ何もしない
   (無理に原因を作りにいかない。ループの主タスクにはしない)
4. 実装中に見つかった **バグ・矛盾の解消**(小規模なら即対応、大規模なら台帳に追記して次反復へ)
5. 上記が尽きたら `feature_roadmap.md` の F-01〜F-05 へ移行(優先度★の数順)

### 2.3 タスク実施の標準手順

1. タスク番号(例:A-6)を **TodoWrite** に登録し in_progress に
2. 関連ファイルを Read し、既存実装を理解
3. 実装/修正を Edit または Write で行う(**CLAUDE.md の命名規則・コード品質ルールに厳密準拠**)
4. 構文チェック・動作検証を行う(§3 参照)。エラーがあれば修正し通過まで繰り返す
5. TodoWrite を completed に

### 2.4 各反復の実施必須項目(**毎反復必ず実施** — CLAUDE.md 準拠)

1. **改善タスク台帳.md の該当タスク行を更新**(状態列を ✅ / 🔵、備考に完了日付とファイルパス)
2. **進捗ダッシュボード.html を更新**(該当項目の状態・進捗率・最終更新日時)
3. **MEMORY に学んだことを記録**(§6 に記録テンプレート)
4. **LOOP_LOG.md に本反復の要約を追記**(§7 に記録テンプレート)
5. **フォルダ配置ルール準拠を確認**(CLAUDE.md §5)

### 2.5 判断待ちのブロック回避ルール

反復中にユーザー判断が必要な選択肢が出た場合:

1. `AskUserQuestion` を出したら、その回答を **5 分待つ**。
2. 5 分応答が無ければ、**影響がない範囲で** 次のサブタスクへ進む(例: 別ファイルの構文チェック、既に方針確定済の作業)。判断が必要な変更(DB スキーマ変更・破壊的操作・大規模書換え・スコープ超過が疑われるもの)は絶対に進めない。
3. 一連のパートを完了する **最後** に、保留になった判断を「未承認のまま実行しなかった項目」として明示し、まとめてユーザーに確認する。
4. 承認後、次反復で保留項目を消化する。

**Why:** 反復ごとに 1 件の判断で止まるとループが進まない。一方、影響の大きい操作を勝手に進めると事故につながる。このルールで「進めるもの」と「止めるもの」を分ける。

### 2.6 反復の終了と次回起動

1. **ScheduleWakeup** を呼び、次の起動を予約
   - `delaySeconds`: **1200 秒(20 分)を既定値とする**。ブロッカー / レビュー待ちの場合は延長可
   - `prompt`: `/loop docs/進捗管理/LOOP_CONTRACT.md を読み、記載の手順で1タスク実装してください`
   - `reason`: 「タスク A-X 完了、次は A-Y に着手」等の具体的説明
2. ループ全体が完了(§5 の停止条件を満たす)したら `ScheduleWakeup { stop: true }` で終了

(`C:\App\ScheduleManagement\db\web_app.db`) への書き込みは**このループでは絶対に行わない**

### 3.4 検証結果の扱い

- **エラー**: そのタスクを completed にできない。原因調査 → 修正 → 再検証を繰り返す

「本番反映待ち」の状態で TodoWrite を completed にしてよい(台帳の状態列には反映待ちである旨を明記)。

## 4. コーディング規約(CLAUDE.md 準拠 — 厳守)

- 変数名・関数名:スネークケース、クラス名:パスカルケース、定数:大文字スネークケース
- インデント:スペース 4 つ(タブ禁止)、1 行 1 命令
- 関数は 1 画面以内、ネスト最大 3 階層、ラムダ式の多用禁止
- コメントは処理の直前行に日本語で(半角カタカナ禁止)
- リソース管理は `with` 文で
- 応答・コミットメッセージ・ドキュメントはすべて日本語

### 4.1 セキュリティ(CLAUDE.md §6 準拠)

- `.env`, `*.pem`, `*.key`, `secrets.json` は読み書き禁止
- `curl`, `wget`, `scp`, `ssh`, `rsync` 等の外部送信は禁止
- `git push`・`pip install`・`WebSearch` は実行前に確認(ask)
- `rm -rf`, `sudo` 等の破壊的コマンドは禁止
- 本番 DB(`db/web_app.db`)には一切触れない。検証は DEV DB(`db/web_app_dev.db`)のみ

## 5. 一時停止・停止条件

以下のいずれかに該当したら、**ループを一時停止**しユーザー確認を仰ぐ:

1. **本番 DB・本番環境への変更が必要と判明**
2. **検証が 3 回連続で失敗**し原因が特定できない
3. **1 タスクの実装で 300 行超のコード変更が必要**と判明(スコープ再確認)
4. **CLAUDE.md の確認必須項目に該当**(ファイル削除・上書き・移動、DB スキーマ変更、外部送信)
5. **既存ガント(project_tasks_gantt.html)との役割整理(タスク 1-3)など、廃止/共存の方針がユーザー判断待ちの場合**
6. **改善タスク台帳のフェーズ0〜4、または §12「必須」項目(#38〜#41)すべてのタスクが完了**
7. **#38(タスク区分マスタの部門分離)の設計方針(dept_id列のNULL扱い・既存データ移行方法)が未確定**

一時停止・完了する場合は `ScheduleWakeup { stop: true }` で自動再開を止め、ユーザーへ状況を報告する。
