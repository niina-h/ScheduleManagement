# LOOP_CONTRACT ／ 自律ループ実行契約書

このファイルは **`/loop` コマンドから読み込まれ、Claude が自律的にタスクを進めるための実行契約書**。
各反復ごとにこの契約書を読み直し、記載順に従って行動する。

- 版数: 1.0(Draft)
- 作成日: 2026-07-23
- 対象プロジェクト: 予定管理システム(ScheduleManagement)
- ループ実行モード: **動的モード(自律ペーシング)**

## 0. ループ起動の呼び出し方(人間向け)

対話セッションで次を入力する:

```
/loop docs/進捗管理/LOOP_CONTRACT.md を読み、記載の手順で1タスク実装してください
```

初回起動後は Claude が自律的に **ScheduleWakeup** を用いてペースを刻む。停止したいときは以下:

- 一時停止: 「一時停止」「pause」「停止して」
- 完全終了: 「ループ終了」「stop loop」

## 1. ミッション(このループの目的)

**予定管理システムを「ガントチャートメイン方式」へ転換するリリースを完成させること**。

現行は「タスク管理から入力 → ガントチャートが引かれる」流れだが、これを逆転し
「**ガントチャートを視覚的に引く → その内容をタスク一覧化する**」方式をメインにする。
週間予定・実績・振り返りは、このガントチャートを起点に一気通貫でつながる形を目指す。

対応順序(上から順に):
1. ガントチャートで先々の計画を立てる(視覚的入力 → タスク一覧化)
2. 翌週の週間予定を立てる(ガント反映ボタン＋定例同時割当＋予定時間手入力)
3. 実績の入力(現行維持の確認)
4. 振り返り(予定 vs 実績の差分を毎日可視化、所属長・管理職も部下状況を把握できる — 新機能)

- 対象タスク台帳: [改善タスク台帳.md](改善タスク台帳.md)(フェーズ0〜4)
- 完了判定: 改善タスク台帳のフェーズ0〜4、全タスクが ✅
- 副次目標: 改善タスク台帳が常に最新の実装状況を反映していること

---

## 2. 実行順序(1 反復 = 1 タスク完遂)

各反復で **1 つ** のタスクを完遂する。並列で複数のタスクに手を出さない。

### 2.1 起動チェックリスト(反復の最初に必ず実行)

1. [改善タスク台帳.md](改善タスク台帳.md) を読み、状態が ⬜ または 🔵 のタスクを取得
2. `git status` で現在のブランチ・uncommitted 変更を確認
3. [LOOP_LOG.md](LOOP_LOG.md) を開き、前回反復の記録があれば確認
4. DEV サーバーが起動中か確認(`dev_server.log` の末尾、または該当ポートの応答)

### 2.2 タスク選択の優先順位

上から順に、最初に該当したタスクを実施する:

1. **フェーズ 0(直前セッションの残タスク 0-6〜0-8)** を先に完遂する — フェーズ2の前提
2. **フェーズ 1(ガントチャート視覚入力)** の残タスクに着手
3. **フェーズ 2(週間予定への反映)** の残タスクに着手
4. **フェーズ 3(実績入力の現状維持確認)** に着手
5. **フェーズ 4(振り返り・新機能)** に着手。4-1(既存分析画面の棚卸し)を必ず先に行い、
   設計(4-4)を経てから可視化画面(4-2/4-3)を実装する
6. 全フェーズ完了後は `feature_roadmap.md` の F-01〜F-05 へ移行(優先度★の数順)
7. 実装中に見つかった **バグ・矛盾の解消**(小規模なら即対応、大規模なら台帳に追記して次反復へ)

### 2.3 タスク実施の標準手順

1. タスク番号(例:A-6)を **TodoWrite** に登録し in_progress に
2. 関連ファイルを Read し、既存実装を理解
3. 実装/修正を Edit または Write で行う(**CLAUDE.md の命名規則・コード品質ルールに厳密準拠**)
4. 構文チェック・動作検証を行う(§3 参照)。エラーがあれば修正し通過まで繰り返す
5. TodoWrite を completed に

### 2.4 各反復の実施必須項目(**毎反復必ず実施** — CLAUDE.md 準拠)

1. **改善タスク台帳.md の該当タスク行を更新**(状態列を ✅ / 🔵、備考に完了日付とファイルパス)
2. **MEMORY に学んだことを記録**(§6 に記録テンプレート)
3. **LOOP_LOG.md に本反復の要約を追記**(§7 に記録テンプレート)
4. **フォルダ配置ルール準拠を確認**(CLAUDE.md §5)

### 2.5 判断待ちのブロック回避ルール

反復中にユーザー判断が必要な選択肢が出た場合:

1. `AskUserQuestion` を出したら、その回答を **5 分待つ**。
2. 5 分応答が無ければ、**影響がない範囲で** 次のサブタスクへ進む(例: 別ファイルの構文チェック、既に方針確定済の作業)。判断が必要な変更(DB スキーマ変更・破壊的操作・大規模書換え・スコープ超過が疑われるもの)は絶対に進めない。
3. 一連のパートを完了する **最後** に、保留になった判断を「未承認のまま実行しなかった項目」として明示し、まとめてユーザーに確認する。
4. 承認後、次反復で保留項目を消化する。

**Why:** 反復ごとに 1 件の判断で止まるとループが進まない。一方、影響の大きい操作を勝手に進めると事故につながる。このルールで「進めるもの」と「止めるもの」を分ける。

### 2.6 反復の終了と次回起動

1. **ScheduleWakeup** を呼び、次の起動を予約
   - `delaySeconds`: **1200 秒(20 分)を既定値とする**。ブロッカー / レビュー待ちの場合は延長可
   - `prompt`: `/loop docs/進捗管理/LOOP_CONTRACT.md を読み、記載の手順で1タスク実装してください`
   - `reason`: 「タスク A-X 完了、次は A-Y に着手」等の具体的説明
2. ループ全体が完了(§5 の停止条件を満たす)したら `ScheduleWakeup { stop: true }` で終了

## 3. 検証コマンド

### 3.1 構文チェック

```bash
python -c "import ast; ast.parse(open('web_app/routes/schedule.py', encoding='utf-8').read())"
```

### 3.2 DEV サーバーの再起動(Python コード変更後は必須)

TEMPLATES_AUTO_RELOAD は HTML テンプレートのみが対象。`.py` を変更したら必ず再起動する。

```bash
# 起動中プロセスの確認・停止
netstat -ano | findstr :5001
taskkill //PID <PID> //F

# DEV 環境で再起動(ポート5001)
FLASK_ENV_LABEL=DEV python run_web.py
```

### 3.3 動作検証(test_client 経由)

DB へ実際に触れる検証は `db/web_app_dev.db` に対してのみ行う(本番 `db/web_app.db` には触れない)。
CSRF ヘッダー名は `X-CSRF-Token`。

### 3.4 検証結果の扱い

- **エラー**: そのタスクを completed にできない。原因調査 → 修正 → 再検証を繰り返す
- **新規に気づいた不具合**: 小規模ならそのタスク内で解消、大規模なら台帳に追記し次反復で対応

## 4. コーディング規約(CLAUDE.md 準拠 — 厳守)

- 変数名・関数名:スネークケース、クラス名:パスカルケース、定数:大文字スネークケース
- インデント:スペース 4 つ(タブ禁止)、1 行 1 命令
- 関数は 1 画面以内、ネスト最大 3 階層、ラムダ式の多用禁止
- コメントは処理の直前行に日本語で(半角カタカナ禁止)
- リソース管理は `with` 文で
- 応答・コミットメッセージ・ドキュメントはすべて日本語

### 4.1 セキュリティ(CLAUDE.md §6 準拠)

- `.env`, `*.pem`, `*.key`, `secrets.json` は読み書き禁止
- `curl`, `wget`, `scp`, `ssh`, `rsync` 等の外部送信は禁止
- `git push`・`pip install`・`WebSearch` は実行前に確認(ask)
- `rm -rf`, `sudo` 等の破壊的コマンドは禁止
- 本番 DB(`db/web_app.db`)には一切触れない。検証は DEV DB(`db/web_app_dev.db`)のみ

## 5. 一時停止・停止条件

以下のいずれかに該当したら、**ループを一時停止**しユーザー確認を仰ぐ:

1. **本番 DB・本番環境への変更が必要と判明**
2. **検証が 3 回連続で失敗**し原因が特定できない
3. **1 タスクの実装で 300 行超のコード変更が必要**と判明(スコープ再確認)
4. **CLAUDE.md の確認必須項目に該当**(ファイル削除・上書き・移動、DB スキーマ変更、外部送信)
5. **既存ガント(project_tasks_gantt.html)との役割整理(タスク 1-3)など、廃止/共存の方針がユーザー判断待ちの場合**
6. **改善タスク台帳のフェーズ0〜4すべてのタスクが完了**

一時停止・完了する場合は `ScheduleWakeup { stop: true }` で自動再開を止め、ユーザーへ状況を報告する。
