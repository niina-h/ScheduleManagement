## 1. 全体フロー(目指す姿)

```
① ガントチャートで先々の計画を立てる(視覚的入力 → タスク一覧化)
      ↓
② 翌週の週間予定を立てる
      ・ガントチャート反映ボタンで該当週の自分の予定にタスクを反映(現行機能)
      ・定例作業も同時に登録・割当(従来通り)
      ・反映されたタスクに予定時間を手入力して保存 → 週間予定作成 完了
      ↓
③ 実績の入力
      ・当日、各ユーザーが予定に対して実績を入力して保存(現行通り)
      ↓
④ 振り返り(新機能)
      ・予定通り進んでいるか、ガント予定と実績入力の差分を毎日見えるようにする
      ・所属長・管理職が部下の状況も把握できるようにする
```

**対応順序**：上から順に①→②→③→④の順で対応していく。①②は既存機能の改善・完成、③は現状維持の確認、④が新規開発。

### 3.1 タスク1-0の詳細(2026-07-23 調査結果)

- **既に本番相当で稼働中**：`base.html`・`project_tasks.html`・`project_tasks_dashboard.html` の「ガントチャート」リンクは全て `planner_bp.planner`(新方式)を指す。旧 `project_tasks_bp.gantt`(`project_tasks_gantt.html`)は直URL打ちでしか到達できない

- **対応方針**：`project_tasks.py` に既にある権限判定(`is_privileged`、所属一致チェック等)を `planner.py` にも適用し、一般ユーザーは自分自身のみ、管理職・マスタは配下メンバーのみを対象にできるよう制限する

### 6.1 タスク4-1の詳細(2026-07-23 調査結果)

- **`project_tasks_dashboard.html`**：プロジェクトタスクの状態管理向け多機能画面(全体ステータス・担当者別テーブル・カテゴリ別グラフ・個人進捗グラフ)。`project_task`の`status`/`progress`/`delay_days`を集計しているのみで、**実績(`daily_result`)とは無関係**。グラフ過多で「情報過多」の主因と推測
- **`comments_review`(daily.py L.586-650)**：配下メンバーの振り返りコメントを期間横断一覧する画面。`is_privileged`+`get_accessible_users`による権限スコープ設計は優秀で、そのまま管理職向け新画面に応用できる。ただしコメントのテキスト表示のみで予定/実績の数値diffは扱っていない
- **重要な既発見**：`get_task_plan_vs_actual`(models.py L.2151-2201)という関数が既に存在し、タスクの日付ベース期待進捗率と`daily_result`の実績時間から`ahead`/`ontrack`/`behind`を判定している。呼び出し元は`daily.html`(L.977-1010)のバッジ表示のみ。**ただしタスク単位・進捗率ベースであり、「その日の予定時間 vs 実績時間」という日次差分ではない**ため、4-2では日次時間単位に再設計が必要
- **方針**：新画面は「`daily_view`の予定/実績列並置レイアウト」＋「`get_task_plan_vs_actual`型のahead/ontrack/behind判定(日次時間ベースに再設計)」＋「`comments_review`の期間横断・権限スコープ」を組み合わせ、グラフ類は極力排して数値・バッジ中心にする

## 13. 統一工程表 自動出力構想（検討段階、2026-08-02〜）

**現在は構想・検討段階。本番システムには一切反映していない。**

### 13.1 構想の狙い

`data/統一工程表.xlsx` を分析し、各部門で上長が手作業（月次・Excel）で作成している
工程表を、ガントチャート・週間予定・日次実績への日々の入力から自動出力できる仕組みに
できないかを検討した。狙いは「上長の集計作業をほぼゼロにする」こと。

モック（画面イメージ・全体の流れ）は Artifact として作成済み：
`統一工程表 自動出力構想（検討段階）`（テストデータ化済み：担当者はAさん/Bさん/Cさん、
案件は案件X/Y、金額・単価は○○表記に置き換え）。

### 13.2 判明した構造（ギャップ分析の要点）

統一工程表は「案件（業務）× 週 × 担当者」の金額・工数マトリクス（計画/消化/残を
週単位で集計）で、現行の `project_task`（日単位バー・進捗%）とは集計軸が異なる。

| 統一工程表に必要な項目 | 現行システムでの対応 | 状況 |
|---|---|---|
| 業務（案件）＋担当者の構造 | ガントチャートの親子ツリー | 対応可 |
| 部門別の切り替え出力 | 部署マスタ・所属切替の仕組みが既にある | 対応可 |
| 進捗率 | ガントチャートの進捗％を流用可 | 対応可 |
| 週単位の時間集計 | 週間予定・日次実績はあるが金額への変換ロジックがない | 要開発 |
| 担当者ごとの工数単価 | 現行システムに単価という概念自体が存在しない | 未対応 |
| 金額（計画・消化・残） | 時間×単価の新しい計算ロジックが必要 | 未対応 |

### 13.3 【重要・未解決】「工数」の定義が確認できていない

実データを検算した結果、統一工程表では **金額 = 工数 × 工数単価** という関係式が
成立している（例：計画金額80・計画工数12・工数単価6.667 → 12×6.667=80）。
ただし「工数」という数値自体が、

- (a) 日次実績の時間を一定基準（例：8時間=1工数）で人日換算した値なのか、
- (b) 見積もり・契約時に別途決められた固定の作業量（時間実績とは連動しない）なのか

**現時点ではユーザー側でも判断がつかず、現場（各部門で工程表を運用している上長）への
確認が必要**と結論づけた。この確認が済むまで、時間入力からの自動集計ロジックの
設計には着手できない（(a)なら自動化、(b)なら別途手入力の仕組みが必要になり、
実装方針が大きく変わるため）。

### 13.4 コスト削減試算（概算レンジ、2026-08-02時点）

上長への実測ヒアリングは未実施のため、**構造的な見積り（概算レンジ）**として算出した。
精度は高くない前提で記録する。

- 7月シートの業務ブロック数：45件（1部門・1か月分）
- 削減が確実な作業：実績ヒアリング・転記、週次の計画/消化/残の自動計算
- 条件付きで削減可能な作業：工数→金額の自動換算（§13.3の確認が前提）
- **概算コスト削減レンジ：月あたり15〜45時間相当**（1業務ブロックあたりのヒアリング・
  転記・集計に5〜15分想定、45業務×週次更新の構造から推定。実測値ではない）

### 13.5 次にやるべきこと

1. **現場確認（最優先）**：各部門の上長に「工数」の定義（§13.3の(a)/(b)のどちらか）を確認する
2. 上長へ「工程表作成に現在何時間かけているか」の実測ヒアリングを行い、§13.4の試算を精緻化する
3. 工数単価の保存場所・閲覧権限の設計（給与に近い機微情報のため、役職ベースのアクセス制御が必須）
