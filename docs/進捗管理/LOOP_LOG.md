### 分析結果の要点

- **決定的な発見**：`weekly_schedule.project_task_id`／`daily_result.project_task_id`が**全件NULL**（DEV DB実測：1,082件・683件）。タスク名の完全一致で補完しようとしても、週間予定のタスク名234種のうち`project_task`と一致するものは**0種**。日常の予定入力語彙（`task_master`由来の自由入力）とガントチャートの計画語彙が完全に別物のため
- 4回の修正はすべて「対応中に何を含めるか」という判定基準を変える方向だったが、結合キー（タスク名一致）が原理的に成立しないため、**どう変えても出力は常に0件かそれに近い状態**だったと推測される
- 理想出力例には、開発状況セクションのインデント（半角2スペース）や、完了・進捗100%のタスクが「対応中」に混在するなど、**ユーザーが開発状況セクションの出力を切り貼りして作成した痕跡**が複数箇所にあった → ユーザーの本当の要求は「対応中を開発状況と同じ書式（中区分見出し＋担当者・進捗）にしたい」という表示形式・情報源の変更であり、判定基準の議論ではなかった
- 理想出力例に登場するタスク名（`動的解析開発　セミナー参加`「訪問先チラシ作成」等）の大半は`project_task`に存在しない。ユーザーの日々の業務語彙は`project_task`側にまだ登録されていない、または粒度が違う
- 見出し語彙が「親タスク名」（動的解析開発、Microsoft365導入）と「中区分名」（AI開発[配筋]、AI開発[上屋]）の2系統混在。後者の一部（AI開発[上屋]）はDBに実在しない中区分だった
- 3階層構造（例：M365パイロット結果反映・プログラム修正 < Microsoft365導入 < ITインフラ）が存在するが、現状の`_parent_task_name`は1階層しか遡らない
- 「上屋作図機能　修正　（穴澤：進捗100%、完了）」の行は実データ（status=未着手,progress=53,担当=新名・早田）と完全に矛盾しており、開発状況セクションからのコピペと推定される。ただしこの矛盾は「当日完了したタスクは対応中に含めたい」という意図の手がかりとして扱う

### ユーザー確定方針（2026-07-28）

**タスク名一致に依存する設計を廃止し、大区分・中区分（category_id/subcategory_id）で結合する方式に切り替える。**
`task_master`にも`project_task`にも共通する区分列を使い、タスク名が一致しなくても「対応中」を中区分単位のまとまりとして集計する。

具体的な変更点7項目をLOOP_CONTRACT.md §1.1.1に記載済み：
1. 「対応中」のグルーピング単位を区分ベースに統一
2. 子タスク行に担当者・進捗・状態を付与
3. 「完了」除外条件を「終了日 < 対象日」に緩和（当日完了は表示）
4. 開発状況の担当者表示を姓のみに統一
5. 開発状況の中区分の並び順を明示的に制御
6. 次回予定の📅絵文字削除、イベント収集をマスタ自身のみに限定
