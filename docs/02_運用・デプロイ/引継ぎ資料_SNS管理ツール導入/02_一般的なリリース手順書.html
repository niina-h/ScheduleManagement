01リリースの基本フロー

各工程は前工程の完了確認を経てから次に進む。飛ばさない・戻らない・記録を残す。この3点だけは徹底する。

STEP 1
事前準備
STEP 2
バックアップ
STEP 3
ステージング検証
STEP 4
本番反映
STEP 5
動作確認
STEP 6
記録

02リリース種別の分類

変更の性質と承認レベルを4分類で判定する。ホットフィックスは事後承認可だが、代わりに障害記録の作成が必須。

種別内容例承認レベル
メジャーリリース破壊的変更・仕様大幅変更v1.x → v2.0部門長承認
マイナーリリース機能追加・非破壊改善v1.1 → v1.2開発リーダー承認
パッチリリースバグ修正・軽微改善v1.1.0 → v1.1.1開発担当者判断可
ホットフィックス緊急バグ対応v1.1.1 → v1.1.2事後承認可

03事前準備チェックリスト

リリース実施前に必ず全項目を確認。チェック漏れがある状態で本番反映してはならない。

コード面

  • 対象機能のテストが全て通っている
  • コードレビュー完了
  • requirements.txt / package.json が最新化されている
  • 開発環境固有の設定（DEBUGフラグ・localhostハードコード等）が残っていない
  • .env / 秘密鍵 / 認証情報がコードに混入していない

環境面

  • 運用端末の空き容量（推奨：最低5GB）
  • 運用端末の Python / Node.js バージョン確認
  • 使用ポートが他システムと競合しないこと
  • 既存稼働システムに影響しないタスク名・サービス名を選定済み

バックアップ面

  • 本番現行版のバックアップ取得完了
  • 本番DBのバックアップ取得完了
  • バックアップ保管先の空き容量確認済み

承認・連絡面

  • リリース種別に応じた承認取得済み
  • 利用者への事前告知完了（メンテナンス時間含む）
  • リリース失敗時のロールバック手順を確認済み

04バックアップ方法

プロジェクト種別ごとにバックアップ方式が異なる。Git 管理／Git 未使用のどちらでも、履歴を残せる形で保存する。

Git 管理プロジェクト（例：予定管理システム）

項目運用
コードGit タグ付け（例：git tag v1.2.0 && git push --tags）
DB別ファイルとしてコピー（例：web_app_20260911.db.bak）
保管期間タグは永続、DBバックアップは最低30日

Git 未使用プロジェクト（例：SNS管理ツール）— 2階層バックアップ

A. リリース版アーカイブ（NAS・正本）と B. ローカルバックアップ（運用PC・ロールバック用）の両方を必ず取得する。A が未取得のまま本番反映してはならない。

種別保管先役割保管期間
A. NAS 正本 \\crown-commune\...\v{バージョン}\ 履歴の正本・監査・過去復元・部門内共有 永年
B. ローカル C:\Backup\SnsManagementTool\ 障害時の高速ロールバック 直近5世代

命名規則

# A. NAS 側（バージョンフォルダ）
v1.2.0
（同一バージョン再リリース時は日時付き：v1.2.0_20260911_1830）

# B. ローカル側（プロジェクト名 + バージョン + 日時）
SnsManagementTool_v1.2.0_20260911_1830

メタ情報（A・B の両方に添付）

VERSION.txt
────────────────────────
バージョン: 1.0.0
リリース日時: 2026-09-11 10:30
作成者: (氏名)
リリース種別: メジャー／マイナー／パッチ／ホットフィックス
変更概要: (一行で)
除外物: .venv, __pycache__, .git, node_modules, *.log
本番配置先: (例: C:\Apps\プロジェクト名)
運用PC: (例: D2KMXR3 / 192.168.70.141)
関連チケット: (あれば)
必須
A（NAS 正本）が未取得のまま本番反映は禁止。B（ローカル）だけでは正本が残らず、後日の監査・引継ぎ・過去復元ができない。NAS アクセス不可の場合は作業を中断すること。
保持ルール
A（NAS）は 全世代を永年保管・削除禁止。B（ローカル）は直近5世代のみ保持し、それ以前は削除可（A に恒久版があるため）。

バックアップコマンド例（Windows / robocopy）

A. NAS へのリリース版アーカイブ（.venv 必須除外）

robocopy "C:\DEV\プロジェクト名" ^
         "\\crown-commune\cloud\Data\商品開発室\50 DEV\54SNS管理ツール\05_開発\03_ソースコード・成果物\v1.0.0" ^
         /E /XD .venv __pycache__ .git node_modules /XF *.log

B. ローカルへのロールバック用バックアップ

robocopy "C:\Apps\SnsManagementTool" ^
         "C:\Backup\SnsManagementTool\SnsManagementTool_v1.0.0_20260911_1030" ^
         /E /XD __pycache__ .venv

共通除外：__pycache__, node_modules, .venv, .git, *.log, ビルド中間物。
★ .venv は必ず除外：環境依存で復元先で動かず、容量だけ肥大化する。

05本番反映の手順

初回リリースと更新リリースで手順が分岐する。更新時は保護ファイルの扱いを最優先で確認する。

初回リリース

#手順
1Python / Node.js 等のランタイム導入確認
2配置先ディレクトリ作成
3ソースコード配置（開発固有ファイルは除外）
4依存パッケージインストール
5設定ファイル（.env相当）を運用端末側で新規作成（コピー禁止）
6起動テスト（フォアグラウンド）
7サービス登録（タスクスケジューラ／Windowsサービス／systemd 等）
8ファイアウォール開放
9起動と疎通確認

更新リリース

#手順
1事前バックアップ取得（本手順書 §04）
2サーバー停止
3ソースコード同期（DB・鍵・ログは絶対に上書きしない）
4依存パッケージ差分適用
5スキーマ変更ありの場合はマイグレーション実行
6サーバー再起動
7動作確認

保護すべきファイル（更新時に上書き禁止）

ファイル理由
*.db / *.sqlite / data.json 等業務データ全て
.secret_key / *.pem / *.key変更でログイン失効・接続断
.env本番接続情報
*.log障害調査に必要
ユーザーアップロードファイル業務資産

06動作確認項目（リリース直後）

9項目のうち1つでも失敗したら §07 のロールバックを検討する。

#確認項目確認方法
1プロセス起動タスクマネージャー or schtasks /Query
2ポートListennetstat -ano | findstr :ポート番号
3ブラウザアクセスログイン画面表示
4ログイン既存ユーザーで正常ログイン
5主要CRUD追加・参照・更新・削除の代表操作
6新機能リリース内容に応じた項目
7既存機能主要業務フローの回帰テスト
8エラーログ直近1時間のログにERROR/CRITICAL がないこと
9他システム影響同一端末稼働の他サービスも正常であること

07ロールバック手順

問題発生時は迷わずロールバック。原因追及は事後で良い。

判断基準
「原因が分かってから戻す」ではなく「10分で復旧しなければ戻す」。復旧優先で判断する。

コード面

  1. サーバー停止
  2. バックアップからソースコードを復元（robocopy /MIR を使用）
  3. 依存パッケージを旧バージョンに戻す（バックアップ内の requirements.txt を使用）
  4. サーバー再起動
  5. 動作確認

DB面

  1. サーバー停止
  2. 現状DBを _failed.db にリネーム（削除しない）
  3. バックアップDBを本番位置にコピー
  4. サーバー再起動
  5. 業務データが復旧していることを確認

ロールバック後の対応

  • 発生事象・原因・対処内容を 障害記録 として文書化
  • 修正版リリース時は再発防止策を明記

08リリース時の禁止事項

下記はいずれも過去にトラブルを起こしている。絶対にやらない。

DO NOT
  • 事前告知なしの本番反映
  • バックアップ未取得のままの上書き
  • 本番DBの直接編集
  • .env / 秘密鍵の他端末コピー
  • 「動くはず」での確認省略
  • 金曜夕方・連休前日のリリース（緊急対応リソースが確保できない）

09リリース連絡テンプレート

利用者への告知はテンプレートを使う。個別文言で書かない。

事前告知（1営業日前推奨）

件名: 【予告】(システム名) v(バージョン) リリースのお知らせ

日時: 2026-09-11 (金) 18:00 〜 18:30
影響: サービス一時停止（約10分間）
内容:
  - (機能追加内容)
  - (バグ修正内容)
ご質問: (連絡先)

リリース完了通知

件名: 【完了】(システム名) v(バージョン) リリース完了

日時: 2026-09-11 (金) 18:15 完了
主な変更:
  - (箇条書き)
確認事項: 通常通りご利用可能です。
不具合がありましたら (連絡先) までご連絡ください。

10リリース履歴の残し方

プロジェクトルートの docs/リリース履歴.md に必ず追記。この記録がない＝リリースしていないと同義。

## v1.2.0 - 2026-09-11
- 実施者: (氏名)
- 種別: マイナーリリース
- 主な変更:
  - 機能A追加
  - 機能Bのパフォーマンス改善
- バックアップ場所: D:\Backup\...
- 確認結果: 正常稼働
- 関連チケット/PR: #123
要点
何を・いつ・誰が・どこにバックアップしたかの4点が揃っていれば、他人でも過去のリリース状況を追跡できる。この4点は絶対に省略しない。
