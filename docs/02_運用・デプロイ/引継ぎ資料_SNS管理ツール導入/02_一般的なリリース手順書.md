# 一般的なプログラムリリース手順書（社内標準）

本ドキュメントは、社内で開発した業務ツールを運用端末へリリースする際の **標準手順** を定める。
特定プロジェクトに依存せず、以下いずれのケースにも適用可能。

- 予定管理システム（Git管理）
- SNS管理ツール（Git未使用・フォルダバックアップ管理）
- その他新規プロジェクト

---

## 1. リリースの基本フロー

```
[事前準備] → [バックアップ取得] → [ステージング検証] → [本番反映] → [動作確認] → [記録]
```

各工程は **前工程の完了確認** を経てから次に進む。飛ばさない・戻らない・記録を残す。

---

## 2. リリース種別の分類

| 種別 | 内容 | 例 | 承認レベル |
|------|------|-----|----------|
| メジャーリリース | 破壊的変更・仕様大幅変更 | v1.x → v2.0 | 部門長承認 |
| マイナーリリース | 機能追加・非破壊改善 | v1.1 → v1.2 | 開発リーダー承認 |
| パッチリリース | バグ修正・軽微改善 | v1.1.0 → v1.1.1 | 開発担当者判断可 |
| ホットフィックス | 緊急バグ対応 | v1.1.1 → v1.1.2 | 事後承認可 |

---

## 3. 事前準備チェックリスト

リリース実施前に **必ず** 全項目を確認。

### 3.1 コード面

- [ ] 対象機能のテストが全て通っている
- [ ] コードレビュー完了
- [ ] `requirements.txt` / `package.json` が最新化されている
- [ ] 開発環境固有の設定（DEBUGフラグ・localhostハードコード等）が残っていない
- [ ] `.env` / 秘密鍵 / 認証情報がコードに混入していない

### 3.2 環境面

- [ ] 運用端末の空き容量（推奨: 最低5GB）
- [ ] 運用端末の Python / Node.js バージョン確認
- [ ] 使用ポートが他システムと競合しないこと
- [ ] 既存稼働システムに影響しないタスク名・サービス名を選定済み

### 3.3 バックアップ面

- [ ] 本番現行版のバックアップ取得完了
- [ ] 本番DBのバックアップ取得完了
- [ ] バックアップ保管先の空き容量確認済み

### 3.4 承認・連絡面

- [ ] リリース種別に応じた承認取得済み
- [ ] 利用者への事前告知完了（メンテナンス時間含む）
- [ ] リリース失敗時のロールバック手順を確認済み

## 4. バックアップ方法（プロジェクト種別ごと）

### 4.1 Git管理プロジェクト

- **コード**: Git タグ付け（例: `git tag v1.2.0 && git push --tags`）
- **DB**: 別ファイルとしてコピー（例: `web_app_20260911.db.bak`）
- **保管期間**: タグは永続、DBバックアップは最低30日

### 4.2 Git未使用プロジェクト（フォルダバックアップ管理）

**バックアップは2階層で運用する**（実務標準）。

#### 4.2.A リリース版アーカイブ（NAS・正本／必須）

バージョンごとにプロジェクト全体を NAS 上へ恒久保管。監査・過去復元・部門内共有の **正本**。

- **保管先**: `\\{NASホスト}\...\{プロジェクト名}\05_開発\03_ソースコード・成果物\v{バージョン}\`
  - 例（SNS管理ツール）: `\\crown-commune\cloud\Data\商品開発室\50 DEV\54SNS管理ツール\05_開発\03_ソースコード・成果物\v1.0.0\`
- **命名**: `v{バージョン}` フォルダ（同一バージョン再リリース時は日時を付与：`v1.0.0_20260911_1030`）
- **除外対象**: `.venv`（★必須）、`__pycache__`, `.git`, `node_modules`, `*.log`
- **格納タイミング**: リリース確定時に必ず格納。未格納のまま本番反映は禁止
- **保管期間**: **永年**（メジャーリリースは特に削除禁止）

#### 4.2.B ローカルバックアップ（運用PC／ロールバック用）

障害時の高速ロールバック用に、運用PC 内に直前版を保持。

- **命名規則**: `{プロジェクト名}_v{バージョン}_{YYYYMMDD_HHMM}`
- **保管先**: 運用PC 内の別フォルダ（例: `C:\Backup\{プロジェクト名}\`）または別ドライブ／別端末
- **保持ルール**: 直近5世代必須。それ以前は削除可（A の NAS 版があるため）

#### 4.2.C メタ情報（A・B の両方に添付）

バックアップフォルダ直下に `VERSION.txt` を必ず添付。

```
バージョン: 1.0.0
リリース日時: 2026-09-11 10:30
作成者: (氏名)
リリース種別: (メジャー／マイナー／パッチ／ホットフィックス)
変更概要: (一行で)
除外物: .venv, __pycache__, .git, node_modules, *.log
本番配置先: (例: C:\Apps\プロジェクト名)
運用PC: (例: D2KMXR3 / 192.168.70.141)
関連チケット: (あれば)
```

### 4.3 バックアップコマンド例（Windows/robocopy）

**A. NAS へのリリース版アーカイブ**

```cmd
robocopy "C:\DEV\プロジェクト名" ^
         "\\NASホスト\...\プロジェクト名\...\v1.0.0" ^
         /E /XD .venv __pycache__ .git node_modules /XF *.log
```

**B. ローカルへのロールバック用バックアップ**

```cmd
robocopy "C:\Apps\プロジェクト名" ^
         "C:\Backup\プロジェクト名\プロジェクト名_v1.0.0_20260911_1030" ^
         /E /XD __pycache__ .venv
```

**除外対象共通**: `__pycache__`, `node_modules`, `.venv`, `.git`, `*.log`, ビルド中間物

**★ `.venv` は必ず除外**：環境依存で復元先で動かず、容量だけ肥大化する。

## 5. 本番反映の手順（一般化）

### 5.1 初回リリース

1. Python / Node.js 等のランタイム導入確認
2. 配置先ディレクトリ作成
3. ソースコード配置（開発固有ファイルは除外）
4. 依存パッケージインストール
5. 設定ファイル（`.env` 相当）を **運用端末側で新規作成**（コピーしない）
6. 起動テスト（フォアグラウンド）
7. サービス登録（タスクスケジューラ / Windowsサービス / systemd 等）
8. ファイアウォール開放
9. 起動と疎通確認

### 5.2 更新リリース

1. 事前バックアップ取得（本手順書 §4）
2. サーバー停止
3. ソースコード同期（**DB・鍵・ログは絶対に上書きしない**）
4. 依存パッケージ差分適用
5. スキーマ変更ありの場合はマイグレーション実行
6. サーバー再起動
7. 動作確認

### 5.3 保護すべきファイル（更新時に上書き禁止）

| ファイル | 理由 |
|---------|------|
| 本番DB (`*.db`, `*.sqlite`, `data.json` 等) | 業務データ全て |
| 秘密鍵 (`.secret_key`, `*.pem`, `*.key`) | 変更でログイン失効・接続断 |
| 環境変数ファイル (`.env`) | 本番接続情報 |
| ログファイル (`*.log`) | 障害調査に必要 |
| ユーザーアップロードファイル | 業務資産 |

## 6. 動作確認項目（リリース直後）

| # | 確認項目 | 確認方法 |
|---|---------|---------|
| 1 | プロセス起動 | タスクマネージャー or `schtasks /Query` |
| 2 | ポートListen | `netstat -ano | findstr :ポート番号` |
| 3 | ブラウザアクセス | ログイン画面表示 |
| 4 | ログイン | 既存ユーザーで正常ログイン |
| 5 | 主要CRUD | 追加・参照・更新・削除の代表操作 |
| 6 | 新機能 | リリース内容に応じた項目 |
| 7 | 既存機能 | 主要業務フローの回帰テスト |
| 8 | エラーログ | 直近1時間のログにERROR/CRITICAL がないこと |
| 9 | 他システム影響 | 同一端末稼働の他サービスも正常であること |

## 7. ロールバック手順

問題発生時は迷わずロールバック。原因追及は事後で良い。

### 7.1 コード面

1. サーバー停止
2. バックアップからソースコードを復元（`robocopy /MIR` を使用）
3. 依存パッケージを旧バージョンに戻す（バックアップ内の`requirements.txt`を使用）
4. サーバー再起動
5. 動作確認

### 7.2 DB面

1. サーバー停止
2. 現状DBを `_failed.db` にリネーム（削除しない）
3. バックアップDBを本番位置にコピー
4. サーバー再起動
5. 業務データが復旧していることを確認

### 7.3 ロールバック後の対応

- 発生事象・原因・対処内容を **障害記録** として文書化
- 修正版リリース時は再発防止策を明記

---

## 8. リリース時の禁止事項

- 事前告知なしの本番反映
- バックアップ未取得のままの上書き
- 本番DBの直接編集
- `.env` / 秘密鍵の他端末コピー
- 「動くはず」での確認省略
- 金曜夕方・連休前日のリリース（緊急対応リソースが確保できない）

## 9. リリース連絡テンプレート

### 事前告知（1営業日前推奨）

```
件名: 【予告】(システム名) v(バージョン) リリースのお知らせ

日時: 2026-09-11 (金) 18:00 〜 18:30
影響: サービス一時停止（約10分間）
内容:
  - (機能追加内容)
  - (バグ修正内容)
ご質問: (連絡先)
```

### リリース完了通知

```
件名: 【完了】(システム名) v(バージョン) リリース完了

日時: 2026-09-11 (金) 18:15 完了
主な変更:
  - (箇条書き)
確認事項: 通常通りご利用可能です。
不具合がありましたら (連絡先) までご連絡ください。
```

## 10. リリース履歴の残し方

プロジェクトルートの `docs/リリース履歴.md` に **必ず** 追記。

```markdown
## v1.2.0 - 2026-09-11
- 実施者: (氏名)
- 種別: マイナーリリース
- 主な変更:
  - 機能A追加
  - 機能Bのパフォーマンス改善
- バックアップ場所: D:\Backup\...
- 確認結果: 正常稼働
- 関連チケット/PR: #123
```
