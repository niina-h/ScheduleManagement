# リリース後メンテナンスとバージョン管理規定

本ドキュメントは、リリース済みプログラムの **継続運用** と **コードバージョン管理** の標準規定を定める。
Git 使用プロジェクトと Git 未使用（フォルダバックアップ管理）プロジェクトの両方に適用する。

---

## 1. バージョン番号ルール（セマンティックバージョニング準拠）

### 1.1 番号体系

```
v[メジャー].[マイナー].[パッチ]
   例: v1.2.3
```

| 桁 | 意味 | 上げるタイミング |
|----|------|----------------|
| メジャー | 破壊的変更 | 既存機能の互換性が失われる変更 |
| マイナー | 機能追加 | 後方互換を保った機能追加 |
| パッチ | バグ修正 | 挙動修正のみ、機能追加なし |

### 1.2 バージョン記載場所

- プロジェクトルートの `VERSION` ファイル（プレーンテキスト1行）
- Python: `__init__.py` の `__version__`
- Web画面: フッターまたは管理画面の「バージョン情報」
- Git 使用時: 対応するタグ (`v1.2.3`)

### 1.3 開発中バージョン表記

- 開発中: `v1.3.0-dev`
- リリース候補: `v1.3.0-rc1`
- 正式リリース: `v1.3.0`
- ホットフィックス: `v1.3.1`

## 2. バージョン管理方式（プロジェクト種別ごと）

### 2.1 Git 管理プロジェクト（例: 予定管理システム）

| 項目 | 運用 |
|------|------|
| 管理単位 | Git リポジトリ |
| バージョン記録 | `git tag v1.2.3` でタグ付け |
| 履歴確認 | `git log --oneline --tags` |
| 過去復元 | `git checkout v1.2.3` |
| ブランチ戦略 | `main`（本番）／ `develop`（統合）／ `feature/*`（機能）／ `hotfix/*`（緊急） |
| コミットメッセージ | 日本語（CLAUDE.md準拠）。1行目に種別+概要 |

**コミット種別プレフィックス例**:

```
feat: 機能追加
fix: バグ修正
docs: ドキュメント
refactor: リファクタリング
test: テスト追加/修正
chore: その他（依存更新等）
```

---

### 2.2 Git 未使用プロジェクト（例: SNS管理ツール）

**バックアップは2階層** で運用する。A（NAS版）が履歴の正本、B（ローカル版）はロールバック用の高速コピー。

#### 2.2.0 2階層バックアップの役割分担

| 種別 | 保管先例 | 役割 | 保管期間 |
|------|---------|------|---------|
| **A. リリース版アーカイブ** | `\\crown-commune\cloud\Data\商品開発室\50 DEV\54SNS管理ツール\05_開発\03_ソースコード・成果物\v{バージョン}\` | 履歴の正本・監査・過去復元・部門内共有 | 永年（メジャーは特に削除禁止） |
| **B. ローカルバックアップ** | `C:\Backup\SnsManagementTool\` | 障害時の高速ロールバック | 直近5世代 |

**★ NAS 版 A が未取得のまま本番反映してはならない**（正本欠落＝バージョン管理の破綻）。

#### 2.2.1 バックアップ命名規則

- **A（NAS）**: `v{バージョン}` フォルダ（例: `v1.2.0`）
  - 同一バージョンで再リリースする場合は日時付き（例: `v1.2.0_20260911_1830`）
- **B（ローカル）**: `{プロジェクト名}_v{バージョン}_{YYYYMMDD_HHMM}`
  - 例: `SnsManagementTool_v1.2.0_20260911_1830`

#### 2.2.2 保管フォルダ構成

**A. NAS 側（正本）**

```
\\crown-commune\cloud\Data\商品開発室\50 DEV\54SNS管理ツール\05_開発\03_ソースコード・成果物\
├── v1.2.0\                     ← 最新
│   ├── (プロジェクト全体、.venv 除外)
│   ├── VERSION.txt              ← 必須
│   └── CHANGES.txt              ← 必須
├── v1.1.2\
├── v1.1.1\

```

**B. ローカル側（運用PC）**

```
C:\Backup\SnsManagementTool\
├── SnsManagementTool_v1.2.0_20260911_1830\    ← 最新
│   ├── (プロジェクト全体、.venv 除外)
│   ├── VERSION.txt
│   └── CHANGES.txt
├── SnsManagementTool_v1.1.2_20260820_1000\
├── SnsManagementTool_v1.1.1_20260805_1500\
├── SnsManagementTool_v1.1.0_20260715_1200\
├── SnsManagementTool_v1.0.0_20260701_0900\
└── (直近5世代のみ保持。それ以前は削除可＝A に恒久版あり)
```

#### 2.2.5 保管期間

**A. NAS リリース版アーカイブ**

| 世代 | 保管場所 | 期間 |
|------|---------|------|
| 全世代 | `\\crown-commune\...\v{バージョン}\` | **永年**（削除禁止） |
| メジャーリリース版 | 同上 | 特に削除禁止 |

**B. ローカルバックアップ**

| 世代 | 保管場所 | 期間 |
|------|---------|------|
| 直近5世代 | `C:\Backup\SnsManagementTool\` | 常時保持 |
| 6世代目以降 | 削除可 | A（NAS）に恒久版があるため |

## 3. リリース後メンテナンス標準運用

### 3.1 定期メンテナンス項目

| 頻度 | 項目 | 内容 |
|------|------|------|
| 毎日 | 稼働確認 | サービス起動状況・エラーログ有無 |
| 毎日 | DBバックアップ | 自動化スクリプトで日次取得 |
| 週次 | ログ整理 | 古いログをアーカイブ or 削除 |
| 週次 | ディスク容量 | 空き容量20%以上維持 |
| 月次 | 依存パッケージ脆弱性確認 | `pip audit` / `npm audit` |
| 月次 | バックアップリストア試験 | 別環境でリストア動作確認 |
| 四半期 | セキュリティレビュー | 認証・権限まわりの点検 |
| 年次 | ランタイム更新検討 | Python / Node.js のバージョン更新 |

### 3.2 監視すべきメトリクス

- サーバープロセスの稼働時間
- CPU / メモリ使用率
- ディスク空き容量
- DBファイルサイズ
- 直近1時間のERRORログ件数
- レスポンスタイム（体感でも可）

### 3.3 障害対応の優先順位

| 重大度 | 症状 | 対応時間 | 対応者 |
|-------|------|---------|--------|
| Sev1 | 全ユーザーが利用不能 | 即時（30分以内） | 全員招集 |
| Sev2 | 一部機能が利用不能 | 当日中 | 担当者 |
| Sev3 | 単機能の不具合、代替手段あり | 数日以内 | 通常対応 |
| Sev4 | 見た目・軽微 | 次回リリース | バックログ |

## 4. 変更管理の運用

### 4.1 変更ログの残し方

| 場所 | 内容 |
|------|------|
| `docs/リリース履歴.md` | プロジェクトルート。全リリースを時系列で |
| バックアップ内 `VERSION.txt` / `CHANGES.txt` | そのバックアップ時点の状態 |
| 障害記録 `docs/障害履歴.md` | 発生・原因・対処・再発防止 |

### 4.2 変更影響の記録

大きな変更時は以下を記録:

- 変更前後の設計比較
- 影響を受ける機能一覧
- 移行手順（データ移行含む）
- ロールバック手順

## 5. Git未使用プロジェクトを Git 化する場合の指針

将来的に Git 導入を検討する際の判断基準。

### 5.1 Git 化するメリット

- 差分管理が容易（フォルダ丸コピーより効率的）
- ブランチで並行開発可能
- コード履歴が細かく追える
- リモート（GitHub/GitLab等）でのバックアップ

### 5.2 移行時の注意

- 既存バックアップは **消さずに保持**（Gitに全履歴は取り込めない）
- 移行前最終バージョンを初回コミットとする
- `.gitignore` を先に整備（DB・秘密鍵・ログ・仮想環境を除外）
- 過去バージョンにアクセスしたい場合はバックアップフォルダから復元

### 5.3 段階的移行案

1. 現在の最新版で Git 初期化
2. `.gitignore` 整備
3. 開発PCでのみ Git 運用開始（リモート未接続）
4. 3ヶ月試行後、社内Git（GitLab等）へリモート化検討

## 6. ドキュメント整備規定

各プロジェクトは以下を **必ず** 保持する。

| ファイル | 内容 | 更新タイミング |
|---------|------|-------------|
| `README.md` | 概要・セットアップ手順 | 初期構築時＋大きな変更時 |
| `VERSION` | 現在のバージョン | 毎リリース |
| `docs/リリース履歴.md` | リリース記録 | 毎リリース |
| `docs/デプロイ手順書.md` | 本番反映の詳細手順 | 手順変更時 |
| `docs/障害履歴.md` | 発生障害と対応 | 障害発生時 |
| `docs/仕様書` | 業務仕様・データ構造 | 仕様変更時 |
| `CLAUDE.md` | Claude Code 行動規約 | 規約変更時 |

## 7. セキュリティ運用（リリース後継続）

- 秘密鍵・パスワードを **定期ローテーション**（推奨: 半年〜1年）
- 退職者・異動者のアカウントを速やかに無効化
- ログイン失敗の異常増加を月次で確認
- 依存ライブラリの脆弱性情報を月次で確認
- 個人情報を含むログは保存期間を定める（例: 90日）
- バックアップ媒体の物理的な管理（施錠場所・持ち出し禁止等）

## 8. チェックリスト（月次運用点検）

- [ ] 全プロジェクトのサービスが正常稼働している
- [ ] 直近1ヶ月のリリースが `リリース履歴.md` に全て記録されている
- [ ] バックアップが規定通り取得されている（直近5世代確認）
- [ ] ディスク空き容量が20%以上
- [ ] 依存パッケージの脆弱性チェック実施
- [ ] ログサイズが肥大化していない
- [ ] `_archive` フォルダの古いバックアップ整理
- [ ] 障害発生があれば `障害履歴.md` に記録済み
