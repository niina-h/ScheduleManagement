01バージョン番号ルール

セマンティックバージョニング準拠。桁の意味を全員で共通理解しないと、承認レベルの判定がぶれる。

1
Major
破壊的変更
既存機能の互換性が失われる
2
Minor
機能追加
後方互換を保った追加
3
Patch
バグ修正
挙動修正のみ
v1.2.3

バージョン記載場所

場所形式
プロジェクトルートVERSION（プレーンテキスト1行）
Python__init__.py の __version__
Web画面フッターまたは管理画面の「バージョン情報」

状態表記

02バージョン管理方式

プロジェクトによって管理方式が異なる。予定管理システムは Git、SNS管理ツールはフォルダバックアップ。

Git 管理

予定管理システム

  • 管理単位：Git リポジトリ
  • バージョン記録：git tag v1.2.3
  • 履歴確認：git log --oneline --tags
  • 過去復元：git checkout v1.2.3
  • ブランチ：main / develop / feature/* / hotfix/*
  • コミットメッセージ：日本語（CLAUDE.md準拠）
フォルダ管理

SNS管理ツール

  • 管理単位：バックアップフォルダ
  • バージョン記録：フォルダ名 + VERSION.txt
  • 履歴確認：バックアップフォルダ一覧
  • 過去復元：バックアップから robocopy 復元
  • ブランチ：なし（1本道の履歴）
  • 変更記録：CHANGES.txt に追記

コミット種別プレフィックス（Git 使用時）

プレフィックス用途
feat:機能追加
fix:バグ修正
docs:ドキュメント
refactor:リファクタリング
test:テスト追加／修正
chore:その他（依存更新等）

2階層バックアップ運用（NAS 正本 + ローカル ロールバック用）

種別保管先役割保管期間
A. NAS 正本 \\crown-commune\...\v{バージョン}\ 履歴の正本・監査・過去復元・部門内共有 永年
B. ローカル C:\Backup\SnsManagementTool\ 障害時の高速ロールバック 直近5世代
必須
A（NAS 正本）が未取得のまま本番反映は禁止。正本欠落＝バージョン管理の破綻。

命名規則

# A. NAS 側（バージョンフォルダ）
v1.2.0
（同一バージョン再リリース時は日時付き：v1.2.0_20260911_1830）

# B. ローカル側（プロジェクト名 + バージョン + 日時）
SnsManagementTool_v1.2.0_20260911_1830

03メンテナンス標準運用

リリース後は放置せず、頻度別に決まった作業を行う。監視・障害対応の優先度も定義する。

定期メンテナンス項目

頻度項目内容
毎日稼働確認サービス起動状況・エラーログ有無
毎日DBバックアップ自動化スクリプトで日次取得
週次ログ整理古いログをアーカイブ or 削除
週次ディスク容量空き容量20%以上維持
月次脆弱性確認pip audit / npm audit
月次リストア試験別環境でバックアップの復元確認
四半期セキュリティレビュー認証・権限まわりの点検
年次ランタイム更新Python / Node.js のバージョン更新検討

監視すべきメトリクス

  • サーバープロセスの稼働時間
  • CPU / メモリ使用率
  • ディスク空き容量
  • DBファイルサイズ
  • 直近1時間のERRORログ件数
  • レスポンスタイム（体感でも可）

障害対応の優先順位

重大度症状対応時間対応者
Sev1全ユーザーが利用不能即時（30分以内）全員招集
Sev2一部機能が利用不能当日中担当者
Sev3単機能の不具合、代替手段あり数日以内通常対応
Sev4見た目・軽微次回リリースバックログ

04変更管理の運用

変更履歴は3つの場所に残し、それぞれ役割を分ける。

変更ログの残し方

場所内容
docs/リリース履歴.mdプロジェクトルート。全リリースを時系列で
バックアップ内 VERSION.txt / CHANGES.txtそのバックアップ時点の状態
docs/障害履歴.md発生・原因・対処・再発防止

変更影響の記録（大きな変更時）

  • 変更前後の設計比較
  • 影響を受ける機能一覧
  • 移行手順（データ移行含む）
  • ロールバック手順

05Git 化する場合の指針

SNS管理ツールなど Git 未使用プロジェクトを、将来 Git 化する場合の判断基準と手順。

Git 化するメリット

  • 差分管理が容易（フォルダ丸コピーより効率的）
  • ブランチで並行開発可能
  • コード履歴が細かく追える
  • リモート（GitHub/GitLab 等）でのバックアップ

移行時の注意

Caution
  • 既存バックアップは消さずに保持（Git に全履歴は取り込めない）
  • 移行前最終バージョンを初回コミットとする
  • .gitignore を先に整備（DB・秘密鍵・ログ・仮想環境を除外）
  • 過去バージョンにアクセスしたい場合はバックアップフォルダから復元

段階的移行案

  1. 現在の最新版で Git 初期化
  2. .gitignore 整備
  3. 開発PCでのみ Git 運用開始（リモート未接続）
  4. 3ヶ月試行後、社内Git（GitLab 等）へリモート化検討

各プロジェクトが最低限保持すべきドキュメントと、更新タイミングを定める。

ファイル内容更新タイミング
README.md概要・セットアップ手順初期構築時＋大きな変更時

07セキュリティ運用

リリース後も継続して守るべきセキュリティ運用ルール。

  • 秘密鍵・パスワードを定期ローテーション（推奨：半年〜1年）
  • 退職者・異動者のアカウントを速やかに無効化
  • ログイン失敗の異常増加を月次で確認
  • 依存ライブラリの脆弱性情報を月次で確認
  • 個人情報を含むログは保存期間を定める（例：90日）
  • バックアップ媒体の物理的な管理（施錠場所・持ち出し禁止 等）
Point
セキュリティ運用は「一度設定したら終わり」ではなく 継続的な確認 がすべて。月次点検（§08）に組み込むことで、担当者が変わっても確実に実施される仕組みにする。

08月次運用点検チェックリスト

毎月1回、以下の項目を全て確認する。1つでも未達があれば対応を実施したうえで完了とする。

  • 全プロジェクトのサービスが正常稼働している
  • 直近1ヶ月のリリースが リリース履歴.md に全て記録されている
  • バックアップが規定通り取得されている（直近5世代確認）
  • ディスク空き容量が20%以上
  • 依存パッケージの脆弱性チェック実施
  • ログサイズが肥大化していない
  • _archive フォルダの古いバックアップ整理
  • 障害発生があれば 障害履歴.md に記録済み
Tip
チェック結果は月次でExcelまたはMarkdownに残す。半年〜1年後に振り返ることで、繰り返し発生している問題（容量ひっ迫・特定サービスの停止頻度など）が可視化される。
