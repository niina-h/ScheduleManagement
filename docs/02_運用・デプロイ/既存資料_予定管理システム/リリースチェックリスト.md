## 3. リリース当日の手順（本番環境向け、実施は別途承認後）

既存の [`docs/デプロイ手順書.md`](デプロイ手順書.md) の手順に従う。今回はDBスキーマ変更を伴うため、以下の点に注意する。

### 3-1. 事前準備

1. リリース予定日時をユーザーへ事前告知（作業中は一時的にアクセス不可になる旨）
2. 本番サーバーの状態確認：`bat/server_status.bat`
3. 本番DBの手動バックアップを取得（[`docs/backup_recovery.md`](backup_recovery.md) 参照。自動バックアップに加えてリリース直前の世代を明示的に残す）

### 3-2. デプロイ

DBスキーマ変更を伴うが、**トランザクションデータ（予定・実績）は本番のものを維持する**ため、`bat/deploy_code.bat`（プログラムのみ更新）を使用する。`_migrate_schema` がアプリ起動時に自動でスキーマを追加するため、`deploy_transaction.bat`／`deploy_full.bat`（DB上書き系）は使用しない。

1. 本番サーバーを停止（`docs/デプロイ手順書.md` 第6章）
2. `bat/deploy_code.bat` を実行してプログラムファイルを同期
3. 本番サーバーを起動
4. 起動ログでマイグレーションが正常完了しているか確認（エラーが出ていないこと）

### 3-3. リリース後の動作確認

`docs/デプロイ手順書.md` の「更新後の確認事項」に加え、本リリース固有の確認：

- [ ] ログイン後、既存ユーザーのロール表示が正しいこと（旧ロール文字列が自動的に4段階へ正規化されていること）
- [ ] 既存の週間予定・日次実績・タスクデータが従来通り表示されること

## 4. ロールバック方針

`docs/デプロイ手順書.md` 第「ロールバック」章の手順に従う。追加の注意点：

- 今回はDBスキーマに列・テーブルを**追加**するのみで、既存列の削除・型変更は行っていない。そのため、プログラムだけを前バージョンに戻せば（DBはそのままで）動作する可能性が高い。
- ただし新しいテーブル（`user_affiliation`等）にデータが書き込まれた後にロールバックすると、旧バージョンのコードはそのテーブルを参照しないため、書き込まれたデータは一時的に不可視になる（削除はされない）。
- 判断に迷う場合は、DBもリリース直前のバックアップへ戻すこと（3-1で取得した世代を使用）。
