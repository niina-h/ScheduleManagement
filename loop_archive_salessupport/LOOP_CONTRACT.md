## 3. 実行順序(1 反復 = 1 タスク完遂)

各反復で **1 つ** のタスクを完遂する。並列で複数のタスクに手を出さない。

### 3.1 起動チェックリスト(反復の最初に必ず実行)

1. `docs/進捗管理/営業日報_移設計画_進捗管理.md` §3 を読み、状態が ⬜ または 🔵 のタスクを取得
2. 現在のブランチ / uncommitted 変更を `git status` で確認(このリポジトリは非 git — スキップ可)
3. `docs/進捗管理/LOOP_LOG.md` を開き、前回反復の記録があれば確認
4. `docs/進捗ダッシュボード.html` を参照し、現在の全体進捗率を確認

### 3.2 タスク選択の優先順位

上から順に、最初に該当したタスクを実施する:

1. **§2 実態把握で「要確認」となっているタスク**(既にコード実装済かの検証を優先)
2. **フェーズ 1・2 の残タスク**(下記 §3.6 参照。フェーズ 3 に手を出す前にこれを消す)
3. **依存関係の少ないフェーズ 3 タスク**(3-1〜3-8 系を先、3-14〜3-17 を後)
4. **未実装マーカー(TODO / 未実装)の解消**
5. その他 §3 フェーズ 3 の残タスク

### 3.3 タスク実施の標準手順

1. タスク番号(例:3-4)を **TodoWrite** に登録し in_progress に
2. 関連ファイルを Read し、既存実装を理解
3. 実装/修正を Edit または Write で行う(**新規フォームは §5 の命名規則 / CLAUDE.md §2 に厳密準拠**)
4. ビルドを走らせて確認(§4 参照)。エラーがあれば修正しビルド通過まで繰り返す
5. TodoWrite を completed に

### 3.4 各反復の実施必須項目(**毎反復必ず実施** — CLAUDE.md 準拠)

1. **進捗管理.md の該当タスク行を更新**(状態列を ✅ / 🔵、備考に完了日付とファイルパス)
2. **進捗ダッシュボード HTML を更新**(KPI・フェーズバー・更新台帳)
3. **MEMORY に学んだことを記録**(§7 に記録テンプレート)
4. **LOOP_LOG.md に本反復の要約を追記**(§8 に記録テンプレート)
5. **フォルダ配置ルール準拠を確認**(CLAUDE.md §5)

### 3.4b 判断待ちのブロック回避ルール (2026-07-22 追加)

反復中にユーザー判断が必要な選択肢が出た場合:

1. `AskUserQuestion` を出したら、その回答を **5 分待つ**。
2. 5 分応答が無ければ、**影響がない範囲で** 次のサブタスクへ進む (例: 別ファイルの TODO 解消、既に方針確定済の作業)。 判断が必要な変更 (DB 変更・破壊的操作・大規模書換え・スコープ超過が疑われるもの) は絶対に進めない。
3. 一連のパートを完了する **最後** に、保留になった判断を「未承認のまま実行しなかった項目」として明示し、まとめてユーザーに確認する。
4. 承認後、次反復で保留項目を消化する。

**Why:** 反復ごとに 1 件の判断で止まるとループが進まない。 一方、影響の大きい操作を勝手に進めると事故につながる。 このルールで「進めるもの」と「止めるもの」を分ける。

### 3.5 反復の終了と次回起動

1. **ScheduleWakeup** を呼び、次の起動を予約
   - `delaySeconds`: **120 秒(2 分)を既定値とする**(ユーザー指示 2026-07-22、推移: 300 → 120 → 600 → 300 → 120)。ブロッカー / レビュー待ちの場合のみ 1200 秒以上へ延長可
   - `prompt`: `/loop docs/進捗管理/LOOP_CONTRACT.md を読み、記載の手順で1タスク実装してください`
   - `reason`: 「タスク 3-X 完了、次は 3-Y に着手」等の具体的説明
2. ループ全体が完了(§9 の停止条件を満たす)したら `ScheduleWakeup { stop: true }` で終了

### 3.6 フェーズ 1・2 の残タスク(フェーズ 3 と並行で処理可能)

- **1-1**: 実機で「営業活動時間コンボ」の表示有無確認(Read で `T_SalesDetail.Designer.cs` の `comboBox7` を確認)
- **1-2**: 帳票テンプレート現物突合(`Files/tpl/rap_SalesReport.xlsx` の Read で対応列を検証)
- **1-3**: 旧 DLL 対応表(`docs/_archive/00_既存資料/` を参照)
- **2-1〜2-5**: 業務側合意待ち — **ループでは触らない**(§6 一時停止条件)

```bash
# CLI ビルド(exe を出力)
dotnet build "SalesSupportApp/SalesSupportApp.csproj" -c Debug 2>&1 | tail -20
```

### 4.2 実行中プロセスの停止 → リビルド → 起動(feedback-exe-rebuild の承認済ルール)

```bash
# 起動中なら taskkill、続けて build、成功したら exe 起動

dotnet build "SalesSupportApp/SalesSupportApp.csproj" -c Debug
```

### 4.3 ビルド警告 / エラーの扱い

- **エラー**: そのタスクを completed にできない。原因調査 → 修正 → 再ビルドを繰り返す
- **新規警告(自分のコードに起因)**: そのタスク内で解消してから completed
- **既存警告**: 触らない(ノイズ削減)

## 5. コーディング規約(CLAUDE.md 抜粋 — 厳守)

### 5.1 命名規則(Python は当プロジェクトでは C# だが、対応する規約)

- 変数・メソッド: パスカルケース(C# 慣習)、あるいはローカル変数は必要に応じ camelCase
- クラス: パスカルケース(例:`SCR_C_Contact`、`DB_ContactAccess`)
- 定数: 大文字スネークケース(例:`MAX_RETRY_COUNT`)
- UI 要素: 種別接頭辞(`txtUserName`、`btnSubmit`、`lblStatus`、`chkAgree`、`cmbCountry`、`lstItems`、`grpLogin`、`pnlMain`、`tabMain`)
- 既存の C# コードの命名を優先(既存が `mDBCon` 等ハンガリアンなら踏襲)

### 5.2 コード品質

- インデント:スペース 4 つ
- 1 行 1 命令、関数末尾 `:`(Python 系)、C# は既存スタイルに合わせる
- ネスト最大 3 階層
- ラムダ式の多用禁止 → 明示的なメソッド定義を推奨
- コメント:処理の直前行に日本語で
- リソース管理:C# は `using` 文で管理(`XLWorkbook`・`SqlConnection` 等)

### 5.3 ファイルヘッダー必須

全 `.cs` ファイル先頭に:

```csharp
// ファイル名: SCR_C_Contact.cs
// 概要:      SCR-C 客先コンタクト記録 コードビハインド (v0.6.5)
```

### 5.4 セキュリティ

- `.env` / `*.pem` / `*.key` / `secrets.json` は **触らない**
- `App.config` の DB 接続情報は **平文のまま**(セキュリティ移行は別タスク)
- ユーザー入力のサニタイズ必須
- SQL は **ストアドプロシージャ経由のみ**(直接 SQL 文の埋め込み禁止 — 既存コードのパターンに従う)

## 6. 一時停止条件(ループが判断すべきブロッカー)

以下のいずれかに該当したら、**ループを一時停止**しユーザー確認を仰ぐ:

1. **業務側合意待ちのタスクにしか着手できない**(§4-1〜4-3 の意思決定待ち系)
2. **ビルドが 3 回連続で失敗**し原因が特定できない
3. **既存の重要ファイル(旧 DB 定義・本番接続設定)を書き換える必要が発生**
4. **CLAUDE.md の確認必須項目**(ファイル削除・上書き・移動、外部送信、DB 変更が旧 DB に影響しうる)
5. **1 タスクの実装で 300 行超のコード変更が必要**と判明(スコープ再確認)
6. **フェーズ 3 の 17 タスクすべてが完了** → §9 停止条件へ

一時停止する場合:
- `ScheduleWakeup { stop: true }` で自動再開を止める
- ユーザーへ「ブロッカー内容」「必要な指示」を明記して報告

## 9. 停止条件(ループを完全終了する条件)

以下いずれかで `ScheduleWakeup { stop: true }` を発行し、ユーザーに完了報告:

1. **フェーズ 3 の 17 タスクすべてが ✅**(M3 完了)
2. **業務側合意待ちタスクだけが残った**(フェーズ 2 の 5 タスクは通常ここで停止する)
3. **ユーザーが「ループ終了」「stop loop」等で明示的に停止**
4. **重大なブロッカーが発生**し、独力で解消できない
5. **1 反復の実施時間が非現実的に長くなる**(参考:1 反復 30 分超は停止推奨)
