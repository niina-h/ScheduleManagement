## 1. スコープ

### 1.1 対象(第 1 弾)

- 旧「営業日報作成ツール」の**入力・帳票出力・データ移行**
- 新ツール側の受け皿:`T_SalesDetail` 画面／日報出力(`Codes/Rap_SalesReport.cs`)／3 テーブル
- **DB 移行**:現行 `SalesSupportDB_` → 新 `SalesSupportDB_Integration` へコピー、以後の開発・本番運用は新 DB に一本化

### 1.2 対象外(第 2 弾以降)

- 週間予定表・訪問データ・各抽出ツール
- 内部計算ロジックの厳密再現(実機動画で別途確認)
- **Web 版の顧客情報単位検索の改善・Excel 取込機能**(末尾 §8 に記録)

### 1.3 基本方針

> **作り直しではなく "差分埋め"**。旧フォームの再現ではなく、新画面が旧の全項目を満たすかを項目単位で照合し、不足のみ補う。

## 5. データベース移行戦略(重要)

### 5.1 全体方針

- 現行 DB (`SalesSupportDB_`) を **コピー**して新 DB (`SalesSupportDB_Integration`) を作成する
- 新 DB で開発・検証を進め、**そのまま本番昇格**させる(検証環境を別に立てない)
- 開発期間中、**旧 DB は本番運用を継続**するため、旧 DB と新 DB でデータが乖離する
- 切替時にこの差分を新 DB へ **リコンサイル**して、旧 DB → 新 DB へ切り替える

### 5.2 DB 名称一覧

| 区分 | データベース名 | 用途 | 期間 |
|---|---|---|---|
| 旧(現行本番) | `SalesSupportDB_`(指示のとおり) | 現行本番運用 | T0 まで書込あり、T1 以降は読取専用 |
| 新(開発→本番) | `SalesSupportDB_Integration` | T0〜T1 は開発、T1 以降は本番 | T0 で旧のコピーとして誕生 |

> **確認事項**:現行 `App.config` の `gInitialCatalog` は `SalesSupportDB`(末尾アンダースコアなし)と記載されている。指示書きの `SalesSupportDB_` と表記が異なるため、**実 DB 名の正式表記を運用側で確認**すること。以降の記述は指示のままとする。

### 5.3 想定タイムライン

```
        T0                               T1        T2
        │                                │         │
旧DB    ●━━━━━本番運用継続(書込あり)━━━●━━━読取専用━━→(保管)
        │                                │
新DB    └──コピー→●━━開発・検証━━━━━●━本番━━━━→
                                         ▲
                                         差分リコンサイル＋接続切替
```

- **T0**:旧 DB のスナップショットを取得し、新 DB を作成(フェーズ 1 タスク 1-5)
- **T0〜T1**:開発期間。新 DB で改修・検証。旧 DB では本番運用が続く
- **T1**:切替日(M6)。旧 DB の差分を新 DB へ適用 → 接続先切替
- **T2 以降**:旧 DB は読取専用アーカイブとして一定期間保管(ロールバック用)

### 5.4 差異が発生するパターン(切替時にリコンサイルすべき対象)

| 種別 | 具体例 | リコンサイル方針 |
|---|---|---|
| 新規登録 | 開発期間中に旧 DB に登録された営業案件・訪問データ・週間予定 | 主キー衝突を確認しつつ新 DB へ INSERT |
| マスタ更新 | 会社・支店・顧客・利用者・エリア・業務№・大項目／小項目／キーワードの追加/変更 | 更新日時ベースで抽出、新 DB へ UPSERT |
| ログ | `T_Log`(EventLog)の追加分 | 参考として旧 DB のログを新 DB へ追記 or アーカイブ側で保管 |
| 共通設定 | `M_CommonSetting` 等の管理者変更 | 差分適用 |
| ストアドプロシージャ | 新 DB でのみ改修されたストアドが旧 DB に無い(逆はゼロが望ましい) | 切替直前に片肺状態を再確認 |

**注意**:バッチが自動で書き込むテーブルや、`T_BiddingInfo` の取込結果などもリコンサイル対象になりうる。フェーズ 1 で **書込対象テーブル一覧**を洗い出しておくこと(タスク 1-5 の副産物)。

### 5.5 切替手順(骨子)

1. 旧 DB `SalesSupportDB_` を **読取専用**に切替、または書込を一時停止(利用者へ事前通知)
2. 旧 DB の最終スナップショット取得
3. 開発期間中の差分を抽出(更新日時／トリガーログ／全件比較のいずれか)
4. 新 DB `SalesSupportDB_Integration` へ差分適用(外部キー整合と適用順に注意)
5. 検証:件数一致・代表画面表示・EventLog 記録
6. アプリの接続先を `SalesSupportDB_Integration` に切替(`App.config.gInitialCatalog` を変更した ClickOnce 更新版を配布)
7. 疎通確認後、利用者に切替完了を通知
8. 旧 DB は読取専用のまま一定期間保管(ロールバック備え)

### 5.6 DB 切替に伴うリスク(§7 に集約)

- リコンサイル漏れによる本番データ欠損 → §7 R6
- ストアドの片肺改修 → §7 R7
- ClickOnce 配布漏れ端末が旧 DB を掴み続ける → §7 R8
- Always Encrypted 証明書配布 → §7 R5

### 5.7 開発中の運用ルール

- **新 DB で行った DB 変更は必ず記録**(このドキュメントの §9 変更履歴 or 別紙 DB 変更ログ)
- **旧 DB は開発者が触らない**(ストアド追加・列変更を旧 DB に流さない)
- **開発用アプリの `App.config` は `SalesSupportDB_Integration` を向ける**。誤って旧 DB を向いたビルドを配布しないこと
