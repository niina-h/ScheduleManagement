## 2026-07-21 反復 #022(続き2:ユーザーによるFDHostサービス復旧)

- タスク: **FDHostサービスの復旧作業(ユーザー主導、対話形式で支援)**
- 結果: ✅ **FDHostサービス復旧完了**(通信エラー解消)、母集団化(クロール)は次回反復で継続確認
- 変更内容(すべてユーザーがサーバーへ直接ログインして実施、Claude は原因切り分けと手順案内のみ):
  - Windows サービス一覧で `SQL Full-text Filter Daemon Launcher (SQLSTANDARD)` が「停止」状態と確認
  - サービス開始を試みると「エラー 1069:ログオンに失敗したため、サービスを開始できませんでした」
  - サービスのログオンアカウントを確認したところ `NT SERVICE\MSSQLFDLauncher$SQLSTANDARD`(NT Service 仮想アカウント)
  - `secpol.msc`(ローカルセキュリティポリシー)の「サービスとしてログオン」権利一覧を確認 → **この仮想アカウントが登録されておらず、ドメイン管理者のみが登録されている状態**と判明。これが根本原因
  - ローカルポリシーの直接編集ができない状況だったため、**SQL Server 構成マネージャー経由でログオンアカウントを既存のドメインアカウントに変更**する方針に切替(構成マネージャー経由だと権限設定も自動で整うため)
  - 変更後、サービスの開始に成功(「停止」→「実行中」)
- 動作確認:
  - `EXEC sp_fulltext_service 'restart_all_fdhosts';` を実行 → 以前は「権限なし」(`CrownSSDAdmin`)、`sa` でも FDHost 通信エラーが出ていたが、サービス復旧後はエラーなく完了
  - `SELECT COUNT(*) FROM T_SalesWork WHERE CONTAINS(SalesNaiyou, N'樋門');` を実行 → **以前の「FDHostプロセスとの通信エラー(0x8007042d)」は解消**、クエリ自体は正常に実行できた(結果は0件、後述の理由により)
  - `FULLTEXTCATALOGPROPERTY('SalesSupportFTS', 'ItemCount')` はまだ `0` のまま。`ALTER FULLTEXT INDEX ON T_SalesWork START FULL POPULATION` を明示実行したが「既にアクティブ」の警告のみで ItemCount は増えず。サービス再起動直後で内部同期に時間がかかっている可能性が高いが、原因は本反復終了時点で未確定
- 他システムへの影響確認:
  - 変更は FDHost(全文検索専用プロセス)のログオンアカウントと起動状態のみで、SQL Server本体・エージェント・通常のCRUD処理には無関係と判断
  - `CrownSSDAdmin` 権限では他データベースの内部を確認できないため、逆に他システムへ影響を与えることも技術的にできないことを確認
  - 万一他システムも全文検索機能を使っていた場合、今回の対応はそれらの復旧にも寄与する側であり悪影響はない
